# macOS 分支检查与交回

这份检查单交给接手独立分支的 macOS agent，用原生文件系统检查计划封存、执行捕获和资料获取路线。先读仓库的 [agent 入口](../../AGENTS.md)、[文档约定](../DOCUMENTATION.md)和[机器文档契约](../../machine/AGENT-INSTRUCTIONS.md)。分支身份、已有证据的来源、测试命令和结果包字段都在[交接记录](../../machine/changes/macos-pr1-validation-handoff-20261030.json)。

本轮交接在原生 macOS 实测前建立执行步骤。此前检查来自 Windows 与受控目录别名前提；原生 macOS 的裁定需要新的实际执行和结果回收。完成后把结果交回维护者，合并与发布由维护者另行决定。

## 先保护现有材料

- 核对收到的独立分支与交接记录中的输入身份，记录工作树已有变动。保留 PR 原始版本、已有评审、首次方案、首稿、旧快照和发布附件。
- 每个试验用新 fixture 和新结果目录。结果记录放在计划目录外，避免测试记录被 READY 当作计划内容。失败后保留现场，重跑另建目录。
- 使用当前普通用户，读取现成系统链接及其父目录的身份。通过已有 `/var/tmp` 与 `/tmp` 的可写临时区创建 fixture；不使用 sudo，不创建或修改系统链接，不改变系统权限或全局代理。
- 延续现有首稿封存与 revisor 修订机制。这里的工程检查无需新建研究首稿，也无需重做已有研究结果。修复需求和研究内容修订各自保留来源与接受范围。

## 先查物理路径是否真正分离

系统祖先链接获准后，同一目录可能同时写成 `/var/...` 与 `/private/var/...`，或 `/tmp/...` 与 `/private/tmp/...`。只比较路径文本会把它们当成两个目录。已有 READY 的源目录可能直接满足“已有封存目录”的内容检查，随后在源目录写入 ARCHIVED，返回成功却没有创建独立副本。子目录别名也可能先让复制进入源树，再在末次源检查时失败。

验收条件是：在创建临时封存目录、复制文件或写 ACK 之前，按解析后的物理路径拒绝源与目标相等、目标包含源、源包含目标三种关系。解析已有源和可能尚不存在的目标时，要保留原有链接拒绝检查。物理路径规范化不应把用户可写链接变成可接受入口。

对两组系统别名分别执行下面的矩阵，并交换两种拼写再做一次。先确认机器上的真实映射；映射缺失或无权使用时记录未执行的具体行。

| 新 fixture 中的关系 | 应观察到的行为 |
| --- | --- |
| 源与目标解析为同一目录 | 拒绝；源内容与 READY 不变；无新增 ACK、封存目录或临时封存写入 |
| 目标解析为源的子目录，目标尚不存在 | 在任何封存写入前拒绝；源树不被新增目标污染 |
| 目标解析为包含源的现有祖先 | 在任何封存写入前拒绝；现有祖先与源均不变 |
| 源与目标是不同的同级目录，路径穿过获准系统祖先 | prepare、check、seal 成功；源和副本内容相符，目录及文件确实各自独立；重复 seal 使用既有回执 |
| 源、祖先、成员或目标经过用户可写位置的符号链接 | 拒绝；保留已有目标和回执内容 |

封存前后记录目录及文件身份、READY、ACK 和临时封存路径。对拒绝行同时观测临时目录创建、复制与 ACK 写入入口是否被调用；只查看最终目录列表无法发现已被清理的短暂写入。成功行既要比较内容，也要检查文件身份和链接数，确认封存副本没有与源共享同一个文件。具体 fixture 布局和观测入口见交接记录的 `native_cases`。

## 再查 capture 和文档输出的合法路径

在两组系统别名下，分别用别名拼写和物理拼写运行现有封存、捕获与 bounded runner 测试。另做一次完整操作：相对 capture-root 选择代码、配置和输入，输出到新的独立目录，确认启动前已保存代码与配置，输入只记录身份；随后改动 fixture 的源文件，原快照继续保留。用户链接、越界路径和已有输出冲突继续按现有契约拒绝。

确认 psutil 可用后，实际运行 `test_inconsistent_capture_is_rejected_before_child_start`。记录 mutation hook 是否命中 `subject.resolve()` 对应的物理文件；捕获过程中改动文件应阻止子进程启动，退出失败，启动标记与执行回执均未生成。依赖缺失时保留 skip 与补测责任。

文档检查使用新的合法文档 fixture，可沿用 [DocumentationFixture](../../tests/test_documentation.py)。仓库根目录本身应为真实目录，祖先可以经过获准的系统链接；报告只放在真实、无链接的 `.scratch` 子目录或仓库外。分别检查别名根配同拼写报告、物理根配同拼写报告；确认合法报告可写，公共正文目录中的报告和穿过用户链接的 `.scratch` 报告被拒绝。

额外检查根目录与报告路径采用相反别名拼写的两种组合，记录解析后的实际位置、命令、退出码及 guard 规则。交接记录保留了该处可能存在拼写方向差异的静态推断；原生结果用于决定是否需要兼容性修订。

## 把离线传输与实际联网分开

先运行资料获取的离线测试，用假 HTTP 会话与限定在测试进程内的确定性公网 DNS 返回值。检查默认 GitHub 直连、显式 `github_proxy`、学术域直连，以及 GitHub 到学术域和学术域到 GitHub 的重定向。每一跳重新选择路线和会话；环境代理已设置时仍关闭继承，直连会话代理为空，显式 GitHub 代理只用于相应跳。现有默认直连重定向用例之外，还需单列启用代理的重定向用例。

如本机已有可用代理且本轮允许实际联网，再把少量公开请求作为独立 live 检查。使用复制的配置和新输出目录，保留逐跳回执与请求预算。不要为本次检查安装服务、修改全局代理或关闭目的地检查。

若 DNS 返回 fake-IP 或保留地址，保留实际解析与拒绝原因；需要时由使用者调整网络后另开运行。离线 stub 的成功归入离线结果，live 的网络阻断归入环境结果。程序拒绝了环境提供的地址，应准确描述该行为，再判断是否涉及实现缺陷。

## 交回什么，何时停止接受

交回机器结果包、原始命令日志、保留的 fixture 位置与一段面向维护者的结论。结果包按交接记录的 `result_bundle` 字段记录实际版本、环境、逐条命令和退出码、测试通过与 skip、文件身份及 ACK 前后变化、以及是否真正生成独立封存副本。新的结果追加为新的运行记录，保留此前证据。

任何物理重叠行到达临时封存、复制或 ACK 写入，或成功行未形成独立副本时，停止接受计划封存修复并交回 P1。其他失败、skip、网络问题与未执行项分别列出受影响的接受条件和下一动作。修订后从新 fixture 复测受影响项目，再由维护者判断分支的下一步。通过本检查也继续沿用已有研究接受与 revisor 边界。
