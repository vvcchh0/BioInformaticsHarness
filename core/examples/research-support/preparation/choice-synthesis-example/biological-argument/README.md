# 工作例：从蛋白定位信息到候选用途

这个例子说明怎样把生物对象、特征形成、标签证据和候选决定写成[一篇连续论证](report.md)。主例使用 UCI Yeast 和 Horton、Nakai 1996 年原论文，保留既有 VAC 补研究的受限负结果；AF2Complex 仅用于对照用途改变时评价怎样随之改变。

先读[正文](report.md)，再沿[来源笔记](source-basis.md)回到原文的定义、分类树和结果表。正文回答的是：八项历史特征与档案定位类别能支持怎样的候选审阅判断，以及下一种用途需要补上什么理由。旧报告已正确区分 vac、VAC、排序量与档案命中，本例补充它们之间的生物学联系。原实验和旧稿保留；这里的新正文是解释与重综合。

## 怎样交给下一位研究者

先核对正文是否给出了当前决定、来源支持的理由、未取得的关键证据和改判条件。仅归档历史结果时，接受这条解释路线即可；准备支持新蛋白或实际定位筛选时，再按正文末尾的具体问题选择新设计。

几种看似完整但仍需修订的写法：

| 写法 | 会改变什么判断；怎样回应 |
|---|---|
| “八项特征预测 VAC，所以可以发现液泡相关基因” | 对象和标签资格发生变化；先定义目标蛋白/基因及其与档案类别的对应，再决定是否需要新参照。 |
| “vac 来自已知定位组，说明当前评价已经泄漏” | 监督来源已知，训练成员重合尚待核实；取得上游成员与数据流再判断，当前保留条件性历史结果。 |
| “命中数增加，就已经能可靠用于筛选” | 要回到同预算参照和既定收益门槛；本例两套主情景均未达完整规则，继续保留负决定。 |
| “记录或脚本检查通过，科学解释也已接受” | 文件、声明和科学证据分别评议；来源支持与推理强度由独立阅读者复核。 |

## 使用已有地图接口

将整个 `biological-argument` 目录复制到一个新工作目录，从 core 运行现有消费者：

```text
python -B -X utf8 -m scripts.research_support.review_coverage --root REVIEW_ROOT --record review-map.json --out checks/review-map.json
```

`review-map.json`、`source-ledger.json` 和 `evidence-map.json` 沿用现有格式。消费者实际读取的是本轮第一方来源笔记和正文，检查记录连接及摘录；原论文由公开链接提供，实际原文阅读另见 `reading-record.json`。`revisor-record.json` 说明为何选择解释路线和仍开放的新用途。

本例没有历史原生地图；当前地图是本轮为解释路线建立的初版。复制后的文件检查与独立科学接受分别记录。测试副本可用于检查缺失阅读依据或关键关系尚未综合却要求交付的错误，原件继续保留。
